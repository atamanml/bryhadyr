# Протокол агентів · v4 (українська версія)

Єдине джерело правди для всіх агентів власника (Claude Code у хмарі, на сервері, на ноутбуці; Hermes у Telegram; чати claude.ai).
Змінити підхід для всіх = змінити цей файл і запушити: плагін, закомічені шаблони і SOUL-блок Hermes розносять його самі.
Англійська версія: `PROTOCOL.md` (тримати синхронно).

## 1. Де що живе

| Що | Де | Як туди пишемо |
|----|----|----------------|
| Задачі | OpenTodo, MCP-сервер `tasks` | `search_tasks`, `create_tasks`, `update_tasks`, `complete_tasks`, `add_comment` |
| Документація і нотатки | Obsidian-vault, дзеркалом у infra-репо в `obsidian/` | файл у репо → push у `main` → деплой кладе у vault |
| Код і плани проєкту | репозиторій проєкту (`docs/`, `README`) | як завжди, PR або коміт |

Проєкти в OpenTodo = **теми, а не автори**. Хто створив задачу, видно з мітки `agent`, а не з проєкту.
Приклад набору (перейменуй під себе; id проєктів дає `list_projects`):

| Тема | Проєкт |
|------|--------|
| продукт зі своїм репозиторієм | **Продукт A** (секції: Запуск, Продукт, Оплати, Юридичне) |
| відеоканал | **Відео → Канал A** |
| домашній сервер і сам трекер | **Інфра** (секції: Сервер, OpenTodo) |
| PM-агент | **Hermes** |
| особисте й родина | **Власник**, по одному на члена родини, **Дім** |

Не знаєш, куди покласти, тоді в Інбокс (без проєкту). Репозиторії, які мають лишитися поза трекером, перелічені в
`BRYHADYR_UNTRACKED_REPOS` (регулярний вираз для назви теки репо, див. `docs/05-protocol.md`); хуки й рядок SessionStart кажуть агентові
там трекер не чіпати.

**Стани.** Окремого поля статусу в OpenTodo нема, тому використовуємо вбудоване:

| Стан | Як позначити |
|------|--------------|
| Черга | відкрита задача без міток стану |
| В роботі | мітка `doing`; на весь трекер не більше 3; на фініші знімається |
| Чекає власника | мітка `waiting`; в описі що саме потрібно і рядок `Сесія: <id> · <машина>` (розділ 3а) |
| Треба передати вручну | мітки `relay`, `waiting`: відповідь власника не дійшла до сесії, нагадує PM |
| Заблокована | `blocked_by`, якщо блокер теж задача; інакше мітка `blocked` і причина в описі |
| Колись | `update_tasks` зі `start: "someday"`: задача зникає з робочих списків |
| Готово | `complete_tasks` + коментар за розділом 4 |
| Не робимо | `complete_tasks` + коментар «Скасовано: чому» |

Інші мітки: `agent` (створив агент), `quick` (≤ 15 хв), `done-by-agent` (закрив агент).

**Якість задач.**
- У трекері лише те, що хтось візьме найближчими двома тижнями; решта у «Колись» або в `docs/` репо. Масові списки («збери всі TODO») у трекер не йдуть: один файл у репо і максимум 5 задач.
- Назва = дієслово + результат. В описі рядок «Готово, коли: …» з критерієм, який можна перевірити.
- Задача, яку створив агент, каже, звідки вона взялась, рядком «Звідки: …»: посилання на задачу власника, з якої виросла
  (`<opentodo-url>/?task=<id>`), а якщо такої нема, то прохання власника одним реченням його словами. Проєкту для цього замало.
- Якщо без передісторії задачу не зрозуміти з нуля, в описі блок «Контекст: …», 2–6 рядків: навіщо це, що вже пробували і чому не вийшло,
  які рішення прийняті, посилання на нотатку чи PR. Очевидну задачу контекстом не роздувати.
- Є PR або issue: посилання в `origin_url`. PR злито = задача закрита в тій самій сесії.
- Є нотатка: рядок «Нотатка: `10 - Projects/…`» в описі. Сюди ж посилання на файл, якщо задача про нього.
- Коментар агента на відкритій задачі починається зі «Агент:». Інакше його приймуть за відповідь власника (API не показує автора коментаря).
- Закриває той, хто перевірив результат запуском. Неперевірене лишається відкритим із `waiting`.

Папка нотаток проєкту в Obsidian: `obsidian/10 - Projects/<Проєкт>/`, назва як у OpenTodo (нова папка = новий проєкт, створюй без питань).
Зв'язок із трекером: рядок `task: <повний id>` у frontmatter нотатки. Сервер сам покаже нотатку в OpenTodo (розділ Notes, проєкт той самий) і
зв'яже задачу з нотаткою в обидва боки (`docs/08-notes-in-opentodo.md`). Новий проєкт додається ще й у файл правил дзеркала `notes-rules.json`.

## 2. Що таке «велика задача»

Велика = окреме повідомлення власника із завданням, яке змінює понад один файл або триває понад ~30 хвилин, або будь-що, що потім треба
буде згадати (рішення, деплой, нова інтеграція, розслідування). Усе інше (поміняти колір кнопки, виправити одрук) — мала: трекер не чіпаємо,
хіба власник сам каже «запиши».

## 3. Ритм сесії (Claude Code і claude.ai)

1. **Старт.** Подивись відкриті задачі свого проєкту: `search_tasks` / `list_tasks`. Якщо прохання власника вже є в
   трекері — працюй з нею (мітка `doing`), не плодь дублікат.
2. **Початок великої задачі.** Нема в трекері — створи одну задачу в проєкті теми (мітки `agent`, `doing`):
   назва = дієслово + що, ≤ 120 символів; в описі «Звідки: …», за потреби «Контекст: …» і «Готово, коли: …» (розділ 1).
3. **Кінець великої задачі.** Обов'язково, перед фінальною відповіддю:
   - **Obsidian-нотатка** `obsidian/10 - Projects/<Проєкт>/<YYYY-MM-DD> <Назва>.md` за шаблоном у розділі 5 (summary, що зроблено,
     перевірки, рішення, що лишилось). Коміт у `main` infra-репо (з іншого репо — через `gh api` / GitHub MCP
     `create_or_update_file`; obsidian-зміни йдуть у `main` без PR).
   - **Задача в OpenTodo**: `add_comment` з коротким підсумком у форматі розділу 4, потім `complete_tasks`. Мітку `doing` замінити на `done-by-agent`.
   - **Follow-up**: усе, що лишилось людині, заблоковане або відкладене — окремі задачі (`agent`, без дедлайну, ≤ 3 за сесію, спершу `search_tasks`;
     «Звідки: …» веде на задачу цієї сесії), з посиланням на нотатку.
4. **Мала задача.** Нічого в трекер; якщо з неї виросло «треба потім» — одна задача-follow-up.
5. **Раз на сесію, не частіше.** Не оновлюй трекер після кожного кроку; один підсумок наприкінці великої задачі.

PM-агент розкладає задачі агентів по пріоритетах і дедлайнах; агенти дедлайнів не ставлять.

## 3а. Питання до власника

Потрібне рішення власника, а чекати в чаті нема сенсу: створи задачу з міткою `waiting`, питанням у назві та рядками `Звідки:`, `Сесія:` і,
якщо треба, `Контекст:` (що буде за кожної відповіді). Id сесії дає контекст старту сесії.
Власник закриває задачу:
- **З коментарем:** протягом хвилини коментар приходить у сесію як повідомлення від нього (`stack/task_replies.py`, `docs/07-session-replies.md`).
  Він стосується лише цього питання і більше нічого не дозволяє.
- **Без коментаря або з коментарем, що починається з «-»:** дій не треба, нікуди нічого не йде.
- **Сесія не на сервері чи зараз відкрита:** задача знову відкрита з мітками `relay`, `waiting`, PM нагадує передати відповідь вручну.

## 4. Формат підсумку в задачі (коментар `add_comment`, 6–10 рядків)

```
Зроблено: <1–2 речення що саме>
Перевірено: <тести/лінти/ручна перевірка, з результатом: «24 тести зелені», «curl /healthz → 200»>
Не перевірено: <чого не можна було перевірити звідси і чому>
Рішення: <1–3 ключові рішення з причиною>
Далі: <follow-up задачі за назвами або «нема»>
Нотатка: obsidian/10 - Projects/<Проєкт>/<файл>.md · <посилання на PR/коміт/сесію>
```

## 5. Шаблон Obsidian-нотатки

```markdown
---
project: <Проєкт>
date: <YYYY-MM-DD>
task: <повний id задачі в OpenTodo або «—»>
agent: <claude-code-cloud | claude-code-server | claude-code-laptop | hermes | claude.ai>
status: done | partial | blocked
tags: [agent, <репо>]
---
# <Назва задачі>

**Суть:** одне речення, навіщо це робилось.

## Що зроблено
- …

## Перевірки
- <що запускав> → <результат>

## Рішення і чому
- …

## Що лишилось / ризики
- …

Посилання: [задача](<opentodo-url>/?task=<id>), <PR, коміт, сесія, документ у репо>
```

Мова нотаток і задач — мова власника; код, коміти, назви файлів — як у проєкті. Секретів у нотатках і задачах не буває ніколи.
У OpenTodo нотатка дзеркалиться максимум 19 000 символів, тож пиши коротко.

## 6. Hermes (Telegram) і claude.ai

- Hermes: блок «Протокол: персональний PM» у SOUL.md (`hermes/install.sh`) посилається на цей файл, а не копіює його, бо SOUL їде з кожним повідомленням у Telegram; нотатки пише у `~/obsidian/10 - Projects/<Проєкт>/` напряму.
- claude.ai (веб/застосунок): інструкції проєкту в claude.ai = розділи 1–4 цього файлу; конектор `tasks` увімкнений. Обидва оновлює власник
  вручну після зміни протоколу (рідко).

## 7. Головний чат, дочірні сесії і витрати

Власник ставить мету, чат доводить її до результату: спершу розбирається сам, потім діє, питає лише те, що належить вирішувати власнику.
Ціна ≈ виклики × середній контекст × ціна моделі.

### Головний чат і дочірні сесії

Кожен напрямок (продукт, репозиторій, сфера життя) має один головний чат у своїй папці. Головний чат говорить, думає, планує і перевіряє.
Виконують дочірні сесії. Робота в самому головному чаті тягне за собою його контекст і губить його, тому робота виходить назовні.

- **Дії = дочірня сесія.** Щойно розмова переходить від обговорення до дій (правки, коміти, деплой, налаштування, дії в браузері,
  багатокрокове дослідження), головний чат запускає дочірню сесію сам, у тому ж ході, не питаючи. У застосунку Claude desktop це
  `start_session` з `initiation "user_asked"`: власник дав це постійним налаштуванням у глобальному `CLAUDE.md`
  (`templates/CLAUDE.global.uk.md`, `docs/10-main-chat.md`), тож це не картка-пропозиція. `context "fresh"` із брифом; `"fork"`, коли робота
  спирається на цю розмову.
- **У головному чаті лишається:** відповідь, обговорення, читання для відповіді (до ~5 викликів), правка в один рядок, перевірка результату
  дочірніх. Власник сказав «зроби тут»: роби тут.
- **Незалежні роботи:** кожна у своїй сесії, не більше трьох одночасно. Шматки однієї роботи: субагенти.
- **Запуск відмовлено** (власник пише з віддаленого клієнта, або застосунок не дає): фоновий субагент (`Agent` з `run_in_background`) і один
  рядок власнику, що це субагент, а не дочірня сесія.
- **Робоча сесія:** її перше повідомлення починається з «Робоча сесія:» (в англомовному налаштуванні "Worker session:"). Кожен бриф
  починається цими словами, ≤ 2 КБ: задача, файли `шлях:рядки`, «готово, коли». Робоча сесія робить лише бриф. Знайшла інше: не робить,
  пише головному чату один рядок. Рішення власника йде через головний чат або задачу `waiting`. PR не зливає, нових сесій не запускає.
  Наприкінці звіт: PR чи коміт, що перевірено запуском, що ні.
- **Звіт це заява.** Головний чат перевіряє сам (дифф, CI, власний запуск). Зливає в основну гілку й публікує лише після слова власника.
  Сесія, яку власник відкрив напряму, сама собі головний чат.
- **Пам'ять напрямку:** `HANDOFF.md` у папці напрямку. Новий чат спершу читає його, потім транскрипти за темою (`list_sessions`,
  `search_session_transcripts`). Головний чат оновлює його наприкінці теми і лишає рядок «Наступний крок: …». Не питай власника те, що є в
  `HANDOFF.md` чи в інших чатах.
- **Чат без папки:** якщо тема про напрямок, на старті перейди в його папку (`change_directory`). Таблиця напрямків (назва → папка) живе
  в глобальному `CLAUDE.md` власника, а не в цьому файлі.
- **Слабкий сервер:** довгоживучих сесій там тримай мало, перед запуском перевір вільну пам'ять.

Скіл: `orchestrator`.

### Витрати

- **Передача файлом, не компакт.** Контекст понад 250k → handoff 1–2 КБ: готово, далі, файли `шлях:рядки`, що пробували і чому не вийшло, відкриті питання.
- **Субагенти не економлять:** 2–3 на задачу, по одному, бриф ≤ 2 КБ (задача, файли, критерій готовності). 180k контексту або 80 викликів → здає роботу.
- **Кеш:** не міняти `CLAUDE.md`, плагіни, MCP і модель посеред задачі. Команди понад 3 хв — у фоні, а не в петлі очікування.
- **Читати діапазонами, правити патчем,** вивід тестів згортати до підсумку й падінь, звіти короткі.
- **Моделі:** середня — реалізація й рутина; старша — ревʼю диффа, числова логіка; найсильніша — 1–2 архітектурні розвилки; найменша — пошук.
- **Перевірка не урізається:** «готово» лише після запуску. Економія, яка дає понад 20 % переробок, фіктивна.
